# Minemasine_mod

Действуй как эксперт по созданию модификаций для DayZ Standalone и старший разработчик на Enforce Script. Работа ведётся над уже существующим модульным серверным модом станков-переработчиков/дробилок **Minemasine_mod**. Не проектируй архитектуру заново и не удаляй уже принятые элементы: сначала учитывай существующую реализацию репозитория, затем вноси только необходимые изменения.

## Текущая архитектура

Мод разделён на два PBO:

- `CN_MiningMachines` — клиентская/общая часть.
- `CN_MiningMachines_Server` — серверная часть с бизнес-логикой.

Текущая структура:

```
Minemasine_mod/
├── README.md
├── CHANGELOG.md
├── CN_MiningMachines/
│   ├── config.cpp
│   └── Scripts/
│       └── 4_World/
│           ├── CN_MiningMachineBase.c
│           ├── ActionStartRecycler.c
│           └── ActionConstructor.c
└── CN_MiningMachines_Server/
    ├── config.cpp
    ├── Scripts/
    │   ├── 4_World/
    │   │   ├── CN_MachineConfig.c
    │   │   ├── CN_MachineConfigManager.c
    │   │   └── CN_MiningMachineBase.c
    │   └── 5_Mission/
    │       └── MissionServer.c
```

Отдельный серверный `ActionStartRecyclerServer.c` не используется.

## Главные архитектурные правила

1. **Не смешивать клиентскую и серверную бизнес-логику.**
   - Клиентский PBO отвечает за регистрацию классов, конфигурацию предметов, кастомные слоты, сетевую синхронизацию состояния и визуально-звуковые эффекты.
   - Серверный PBO отвечает за JSON-конфигурацию, проверки, обработку предметов, таймеры, расчёт шансов и изменение инвентаря.
   - Серверные методы, недоступные клиенту, должны защищаться `#ifdef DZ_SERVER`.

2. **Базовый класс не менять без необходимости.**
   Основной класс — `CN_MiningMachineBase : ItemBase`. Конкретные станки наследуются от него, например `CN_OreExtractor`.

3. **Конфигурация станка определяется через GetType().**
   Серверный менеджер загружает:
   `$profile:ColdNight_SRV_Data\\Mine_Mashines\\<MachineClassName>.json`

4. **Один общий менеджер конфигураций.**
   Используется `CN_MachineConfigManager`. Если каталог конфигураций отсутствует, он создаётся через `MakeDirectory()`. Если JSON конкретного станка отсутствует, создаётся дефолтный файл автоматически при инициализации сервера.

5. **Поштучная переработка.**
   Станок работает через интервальный `Timer`. Каждый успешный тик обрабатывает ровно одну единицу входного стака.

6. **Без потери входного предмета при ошибке результата.**
   Сначала должен быть успешно создан результат текущего цикла, и только после этого разрешается удалить/уменьшить входной предмет. Если результат создать невозможно, цикл останавливается, а входная единица не должна исчезнуть.

7. **Три зоны результата.**
   - `RecycleOutput` — основной результат.
   - `RecycleRare` — редкий результат.
   - Cargo — отходы через `GetInventory().CreateInInventory()`.

8. **Система питания обязательна.**
   Станок работает только при подключённом внешнем кабеле и работающем источнике питания. В скриптах используется `GetCompEM()`, `IsPlugged()` и `IsWorking()`.

9. **ActionConstructor обязателен.**
   `ActionStartRecycler` должен быть зарегистрирован через `SetActions()` базового станка и через существующий `modded class ActionConstructor`. Не удалять эти регистрации и не заменять их альтернативной системой без явного указания.

10. **Совместимость с Enforce Script / DayZ.**
    Не использовать синтаксис, API или конструкции из других языков. Перед добавлением нового API проверять его существование в DayZ. Не вводить несуществующие методы только по аналогии с другими движками.

11. **Стиль кода.**
    Предпочитать простые решения, короткие функции и однострочные функции там, где это не ухудшает читаемость. Не использовать тернарный оператор. Не добавлять пустые заглушки или `placeholder`-код.

## Клиентская/общая часть

### config.cpp

В `CN_MiningMachines/config.cpp` должны быть:

- `CN_MiningMachineBase`;
- пример конкретного предмета `CN_OreExtractor`;
- слоты:
  - `RecycleInput`;
  - `RecycleOutput`;
  - `RecycleRare`;
- `GUIInventoryAttachmentsProps` для этих трёх зон;
- энергетическая конфигурация предмета через существующий `EnergyManager`;
- зависимости и регистрация World script module.

Не менять существующую структуру `CfgPatches/CfgMods/CfgSlots/CfgVehicles` без необходимости.

### CN_MiningMachineBase.c

Базовый класс уже реализует:

- `m_IsProcessing`;
- сетевую регистрацию через `RegisterNetSyncVariableBool()`;
- `SetActions()` с `AddAction(ActionStartRecycler)`;
- `IsProcessing()`;
- `IsPowered()`;
- блокировку слотов `RecycleInput`, `RecycleOutput`, `RecycleRare` во время обработки;
- `OnVariablesSynchronized()`;
- клиентские звуковые и визуальные эффекты.

При работе используется:

- `powerGeneratorLoop_SoundSet`;
- `powerGeneratorStop_SoundSet`;
- `ParticleList.POWER_GENERATOR_SMOKE`.

Не возвращать `ParticleList.BARREL_SMOKE` — этот идентификатор не используется.

### ActionStartRecycler.c

Использовать `ActionInteractBase`.

Действие должно:

- иметь `CreateConditionComponents()`;
- работать с `CN_MiningMachineBase`;
- не запускаться, если станок уже работает;
- не запускаться без питания;
- запускать серверный процесс через `OnExecuteServer()`.

Основная серверная проверка допустимости запуска выполняется методом `Server_CanStartProcess()`, поэтому сервер остаётся авторитетным источником истины.

### ActionConstructor.c

Сохранять:

```cpp
modded class ActionConstructor
{
    override void RegisterActions(TTypenameArray actions)
    {
        super.RegisterActions(actions);
        actions.Insert(ActionStartRecycler);
    }
};
```

## Серверная часть

### CN_MachineConfig

Конфигурация содержит:

```
ProcessTimeSeconds
InputClass
OutputClass
RareClass
WasteClass
RareChance
WasteChance
```

### CN_MachineConfigManager

Использует каталог:

`$profile:ColdNight_SRV_Data\\Mine_Mashines\\`

Для текущего прототипа зарегистрирован `CN_OreExtractor`.

При старте сервера:

1. создаётся каталог, если его нет;
2. для каждого зарегистрированного станка проверяется JSON;
3. отсутствующий JSON автоматически создаётся с дефолтными значениями.

Загрузка выполняется через `JsonFileLoader<CN_MachineConfig>`.

### MissionServer.c

Инициализация конфигурационного менеджера выполняется в `MissionServer.OnInit()`:

```cpp
CN_MachineConfigManager.GetInstance().Initialize();
```

Не переносить эту инициализацию в клиентский PBO.

### Серверный CN_MiningMachineBase.c

В `EEInit()` загружается конфигурация по `GetType()` и создаётся системный `Timer`.

Основные методы:

- `GetMachineConfig()`;
- `Server_CanStartProcess()`;
- `Server_StartProcess()`;
- `Server_ExecuteCycleTick()`;
- `Server_StopProcess()`.

Перед стартом необходимо проверить:

- станок не обрабатывает другой цикл;
- конфигурация загружена;
- питание присутствует;
- входной предмет существует;
- класс входного предмета соответствует `InputClass`;
- количество входного предмета больше нуля;
- основной выход способен принять результат;
- при использовании редкого результата `RecycleRare` способен принять результат.

Каждый тик:

1. повторно проверяется питание;
2. повторно проверяется входной предмет;
3. нормализуются шансы в диапазон 0–100;
4. выполняется один случайный бросок;
5. выбирается один результат: Waste, Rare или Output;
6. результат создаётся первым;
7. только после успешного создания результата из входного стака удаляется ровно одна единица;
8. если вход закончился — обработка останавливается;
9. если результат создать невозможно или пропало питание — обработка останавливается.

Для количества используются существующие API DayZ, например `GetQuantity()`, `GetQuantityMax()`, `SetQuantity()`, `CreateAttachmentEx()`, `CreateInInventory()` и `Delete()`.

## Модель и анимации

Фактические 3D-модели станков, `.p3d`, `model.cfg`, selections, memory points и анимации добавляются поверх существующей логики мода.

При подготовке новой модели необходимо:

1. сохранить существующий класс станка и его серверную логику;
2. определить движущиеся части модели;
3. подготовить корректные selections и pivot/origin;
4. создать совместимый с DayZ `model.cfg`;
5. настроить анимации в соответствии с реальной механикой модели;
6. при необходимости добавить звуки/эффекты;
7. не менять серверную механику переработки только ради подключения новой модели.

## Конфигурация переработки

Пример JSON:

```json
{
    "ProcessTimeSeconds": 1.0,
    "InputClass": "",
    "OutputClass": "",
    "RareClass": "",
    "WasteClass": "",
    "RareChance": 0.0,
    "WasteChance": 0.0
}
```

Шансы трактуются как проценты от 0 до 100. Сначала проверяется WasteChance, затем RareChance, иначе создаётся основной результат.

## Требования к изменениям

Перед изменением кода:

1. Изучи существующую реализацию.
2. Не дублируй уже существующие классы и функции.
3. Не удаляй обязательные элементы архитектуры без явного согласования.
4. Проверяй совместимость с Enforce Script и DayZ Standalone.
5. Учитывай разделение Client/Server PBO.
6. Если меняется архитектурное решение — сначала явно укажи, что именно меняется и почему.
7. После изменения обновляй `CHANGELOG.md`, если изменение относится к архитектуре, API, игровой логике или исправлению совместимости.

Цель — поддерживать компактный, производительный и реально компилируемый DayZ-мод, а не абстрактный пример кода.
