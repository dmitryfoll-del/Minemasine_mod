# Minemasine_mod
Действуй как эксперт в области создания модификаций для DayZ Standalone и старший разработчик на Enforce Script. Мне необходимо сгенерировать чистый, оптимизированный и готовый к продакшену код для модульного серверного мода станков-переработчиков (майнеров/утилизаторов).

### Архитектурные правила и безопасность:
1. Максимальная защита серверного кода: Клиентский PBO должен содержать ТОЛЬКО регистрацию классов, кастомных слотов, сетевых синхронизируемых переменных и визуально-звуковые эффекты. Вся бизнес-логика (чтение JSON, манипуляции с количеством предметов в инвентаре, циклы таймера, математика шансов) должна быть строго изолирована в серверном PBO (компилироваться только внутри #ifdef DZ_SERVER или проверок GetGame().IsServer()).
2. Модульное ядро станков: Создай базовый класс `CN_MiningMachineBase`, унаследованный от `ItemBase`. Любой конкретный станок (например, для руды или плат) должен наследоваться от него и автоматически подтягивать свой собственный файл конфигурации JSON из папки профиля сервера, используя имя своего класса, полученное через GetType().
3. Поштучная переработка стаков (Интервальный таймер): Вместо разового таймера процесс должен идти циклами. Каждый тик интервального таймера (время берется из конфига) станок берет ровно 1 единицу из стака входного предмета и обрабатывает его, динамически изменяя значения количества (Quantity) предметов во входных и выходных слотах.
4. Трехзонная система результатов переработки:
   - Основной продукт: Поштучно настакивается в конкретный слот навесного оборудования машины (`RecycleOutput`).
   - Редкий продукт: С определенным шансом поштучно настакивается в отдельный слот (`RecycleRare`).
   - Отходы/брак: Спавнятся внутри общего инвентаря-сетки станка (Cargo) через GetInventory().CreateInInventory().

### Детальные требования к коду:

1. Файл config.cpp (Для клиентского/общего PBO):
   - Зарегистрируй кастомные инвентарные слоты/аттачменты: `RecycleInput`, `RecycleOutput` и `RecycleRare`.
   - Пропиши базовый класс `CN_MiningMachineBase` и пример наследника `CN_OreExtractor` в CfgVehicles.
   - Настрой блок GUIInventoryAttachmentsProps, чтобы визуально разделить входной, выходной и редкий слоты в интерфейсе инвентаря.
   - Подключи ComponentEnergyProfile для станка: для работы ему обязательно требуется внешнее подключение кабеля (IsPlugged()) и работающий источник питания/генератор (IsWorking()).

2. Скрипты клиентской/общей части (4_World / Common):
   - Определение класса `CN_MiningMachineBase`.
   - Регистрация синхронизируемой переменной `m_IsProcessing` (bool) через RegisterNetSyncVariableBool.
   - Строгая блокировка инвентаря во время работы: переопредели CanReleaseAttachment и CanReceiveAttachment так, чтобы они возвращали false для слотов RecycleInput, RecycleOutput и RecycleRare, если переменная m_IsProcessing равна true.
   - Синхронизация эффектов: переопредели метод OnVariablesSynchronized, чтобы при m_IsProcessing = true на клиентах циклично воспроизводился звук работы ("powerGeneratorLoop_SoundSet") и создавался партикл дыма ("ParticleList.BARREL_SMOKE"), а при выключении запускался разовый звук остановки.

3. Серверные скрипты (Server PBO / Изолированная логика):
   - Структура данных конфигурации: Создай класс `CN_MachineConfig` со свойствами: `float ProcessTimeSeconds`, `string InputClass`, `string OutputClass`, `string RareClass`, `string WasteClass`, `float RareChance`, `float WasteChance`.
   - Менеджер конфигураций: Класс `CN_MachineConfigManager`, который считывает/записывает JSON файлы по пути `$profile:ColdNight_SRV_Data\\Mine_Mashines\\<Имя_Класса_Станка>.json`. Если файла для текущего класса не существует, менеджер обязан сгенерировать дефолтный шаблон автоматически при старте.
   - Серверное расширение (Modded class `CN_MiningMachineBase`):
     - В EEInit() инициализируй загрузку конфига под тип текущего станка.
     - Метод `Server_StartProcess()`: Проверяет наличие энергии от генератора, валидность сырья во входном слоте (количество > 0) и отсутствие переполнения в выходных слотах. Запускает интервальный Timer на основе ProcessTimeSeconds.
     - Метод `Server_ExecuteCycleTick()`: Срабатывает на каждом тике таймера. Снова проверяет питание и наличие предметов. Отнимает 1 единицу от стака входного предмета (если количество падает до 0 — удаляет его). Рассчитывает шанс (рандом 0-100) и распределяет результат: либо мусор в Cargo инвентаря, либо +1 к стаку в RecycleRare, либо +1 к стаку в RecycleOutput. Корректно обрабатывает создание новых предметов в выходных слотах, выставляя им начальное количество 1. Если выходные слоты заполнены до предела или пропало питание — немедленно останавливает таймер.

4. Пользовательское действие (User Action):
   - Напиши класс `ActionStartRecycler`, унаследованный от `ActionInteractBase`.
   - В ActionCondition пропиши условия: действие доступно только при наведении на объект `CN_MiningMachineBase`, станок сейчас не работает (IsProcessing == false), подключен к сети и класс предмета во входном слоте совпадает с InputClass из конфига станка.
   - В OnExecuteServer вызывай запуск цикла переработки на стороне сервера.

Выдай полностью написанные, оптимизированные скрипты для всех указанных компонентов без использования сокращений и пустых заглушек ("placeholders"). Позаботься о строгом разделении клиентского и серверного кода.
